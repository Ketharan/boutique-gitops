# Online Boutique on OpenChoreo — GitOps repository

The GCP microservices demo split into **five projects across two org units**, with real
cross-project dependencies, laid out for Flux CD and promoted through **five environments across
two regions**. Phase 1 of `GCP-DEMO-IMPLEMENTATION.md`, plus the topology decided in
`subtasks/demo_artifact_prep/DEPLOYMENT-ARCHITECTURE.md`.

`boutique` holds the storefront estate. `quality-engineering` holds the traffic simulator that
drives it, as a department in its own right rather than a project of the estate it loads.

Four projects are live. The fifth (`insights`) and one component of `merchandising`
(`shoppingassistant`) are scaffolded under `pending/` and deliberately not applied — they are
blocked on images and on the AI gateway module, not on configuration. See `pending/README.md`.

Generated by transforming the upstream manifests at
`openchoreo/openchoreo:samples/gcp-microservices-demo`, not retyped — images, ports and
environment variables are exactly as upstream pins them (`v0.10.5`).

## Layout

Follows the convention in [`openchoreo/sample-gitops`](https://github.com/openchoreo/sample-gitops):

```
flux/                                  GitRepository + Kustomizations
platform-config/                       Environments + DeploymentPipeline, one set per org unit
namespaces/<ns>/
  namespace.yaml
  projects/<project>/
    project.yaml
    release-bindings/                  one per environment
    components/<component>/            component.yaml + workload.yaml
    resources/                         managed Resources
    bindings/<env>/                    ResourceReleaseBindings
pending/                               scaffolded, not applied — see pending/README.md
```

### Which objects live here, and which never can

| Class | Home | Why |
|---|---|---|
| CRD definitions | the control-plane **Helm chart** | chart-owned and generated |
| `DataPlane`, `ObservabilityPlane`, `WorkflowPlane` | the **installer**, derived per install | they embed `clusterAgent.clientCA` — minted per install, 90-day expiry — plus install-specific gateway hosts. A copy pinned into git is wrong everywhere |
| `Environment`, `DeploymentPipeline` | **here**, in `platform-config/` | no credentials; an Environment names its plane by string only. Upstream models the same split and calls this layer platform config: `openchoreo/openchoreo:samples/platform-config/` |
| `Project`, `Component`, `Workload`, `Resource`, bindings | **here** | the app definition |

**The release pin is not ours.** No binding in this repo sets `spec.projectRelease` or
`spec.resourceRelease`, and none should. The CRD is explicit: *"A set pin is never touched by
controllers — advancing it is left to whoever drives promotion (occ, GitOps, manual kubectl
edit)."* Commit a value and Flux owns the field and reverts every promotion on its next
reconcile. So this repo is the source of truth for **topology and app definition, not for which
release is live where** — deployed versions are cluster state.

## The projects

| Project | Components | Why |
|---|---|---|
| `storefront` | frontend, checkout, productcatalog, cart, currency, payment, shipping, **redis** | The purchase path. Both hubs and everything they call repeatedly stay together. |
| `merchandising` | ad, recommendation | Called only by `frontend`. |
| `notifications` | email | Called only by `checkout`. |
| `traffic-sim` | loadgenerator | Keeps the estate from being idle. Lives in the **`quality-engineering`** org unit, not `boutique`. |
| `insights` | business-portal, insights-api | Reads across storefront and merchandising, so no single domain owns it. **Scaffolded in `pending/`.** |

The split minimises boundary crossings rather than maximising domain purity. A storefront /
catalog / ordering cut looks tidier but forces **8 of 10** services to organisation visibility,
because `frontend` calls eight services and `checkout` six — any cut either hub sits across
leaks most of the estate. This cut leaves **4**.

## The four cross-project edges

```
frontend       (storefront)    -> ad              (merchandising)
frontend       (storefront)    -> recommendation  (merchandising)
checkout       (storefront)    -> email           (notifications)
recommendation (merchandising) -> productcatalog  (storefront)
```

Those four endpoints publish `visibility: [namespace]`; everything else stays project-private.

**On the vocabulary**, because the obvious word is the wrong one. OpenChoreo 1.3.1 spells
inter-project reachability `namespace` on the spec side — *"accessible across all projects in the
same namespace and environment"* (`api/v1alpha1/workload_types.go:107-108`). The published
endpoint enum is `project;namespace;internal;external` and the consumed dependency enum is
narrower still, `project;namespace` (`:100`, `:181`). `organization` **is** a real term in the
API, but it lives on the *status* side — `EndpointStatus.Organization`, carrying an upstream
`TODO: organization endpoint = inter-project endpoint. This is not being used. Refactor later`
(`api/v1alpha1/types.go:12,24`). It is the semantically right word on the wrong side of the API,
which is an easy trap: every boutique project co-resides in the one `boutique` org-unit
namespace, so `namespace` is both the accepted value and the accurate one.

**`productcatalog` is the one people miss.** It lives in `storefront` and is called *into* that
project from `merchandising`, so the organisation-visible service is not only in the "shared"
project. It is also the only edge that is not from the front end, which makes it the most
instructive one in the design.

## The five environments

`platform-config/environments.yaml` and `platform-config/pipeline.yaml`:

```
development  ->  staging-eu  ->  production-eu
             ->  staging-us  ->  production-us
```

Two gates, then two productions promoted independently and never from each other. `development`
sits on the company-wide cluster plane; each region's pair sits on its own namespaced
`DataPlane`. Those two regional planes share one `planeID` with the company-wide plane, so they
are **two plane identities over one physical cluster** — separate environments, separate release
histories, independent promotion, but not geographic or network isolation. State it that way
anywhere this gets described.

Which of the five actually run is **cluster state, not repo state** — the same separation as the
release pins. The boutique goes up *alongside* the existing showroom estate (`doclet`,
`latency-lab`, `oncall`, `url-shortener`) rather than replacing it, with capacity made by parking
rather than deletion, so the likely initial shape is **`development` only, with the four regional
environments parked** at zero and displayed as "(On Demand)". That is the host's constraint, not
the model's, and it does not change anything in this directory.

### Portability — the only install-specific strings in this repo

Three plane names in `platform-config/environments.yaml` are showroom-specific, and they are the
**entire** cloner-edit surface:

| String | Where | What it is |
|---|---|---|
| `ClusterDataPlane/boutique-eu` | 2 environments | derived regional plane, installer-created |
| `ClusterDataPlane/boutique-us` | 2 environments | derived regional plane, installer-created |
| `ClusterDataPlane/company-wide` | 1 environment (`development`) | the showroom's shared cluster plane |

All three are `ClusterDataPlane` references, which is the shape every upstream sample uses
(`ClusterDataPlane/default`). So the cloner's edit is uniform: three names of one kind, rather
than two kinds with different namespace semantics to understand first. The names are still
showroom-specific; the shape is not. `company-wide` is the easiest of the three to miss, because
it looks generic and sits on the one environment that is not regional.

**Why the regional two are cluster-scoped, which is not cosmetic.** `DataPlaneRef` is
`{Kind, Name}` with no namespace field (`api/v1alpha1/types.go:121-129`), and an unqualified
reference resolves in the *Environment's own* namespace
(`api/v1alpha1/environment_types.go:17`). A namespaced `DataPlane/boutique-eu` is therefore
invisible from any namespace except `boutique`, which would stop a second org unit from ever
sharing the regional planes. Cluster-scoped, they can be referenced from anywhere.

**Their blast radius is wider than this repository.** Once a second org unit references
`boutique-eu` and `boutique-us`, those two planes have consumers in more than one namespace.
Deleting or re-deriving them is no longer a boutique-only change, and nothing else in the repo
would say so.

To run this elsewhere, repoint those five `dataPlaneRef` blocks at whatever planes you have, or
create planes under these names. Nothing else in the repository needs editing: every other
reference is cluster-scoped and portable (`ClusterComponentType`, `ClusterProjectType`,
`ClusterResourceType`).

One more line is environment-specific and deliberately left unset: `flux/gitrepository.yaml`
carries `url: https://github.com/REPLACE-ME/boutique-gitops`. Set it at install time rather than
committing a home into the manifest — the repository's home is not yet final, and keeping that
line symbolic means relocating it is a one-line change rather than a rewrite.

**Derive those two planes; never hand-write them.** On the showroom they are two
`derive_plane` calls off `ClusterDataPlane/company-wide` — extend
`read-only-setup/scripts/45-orgs.sh` (:32-71), which copies the source plane's spec *and*
annotations verbatim. That inherits three things that are silent to get wrong: `planeID`, the
per-install cluster-agent CA, and the `openchoreo.dev/networkpolicyprovider` annotation the
data-plane controller reads off the object itself (no spec field, not inherited — without it a
derived plane reconciles fine and loses Hubble metrics, wirelogs and the cell-diagram edges).

**`planeID` is the trap if you do write one by hand.** It is optional, and when unset the
controller falls back to the CR's own *name*. A `DataPlane/boutique-eu` created without
`spec.planeID` becomes planeID `boutique-eu`, no cluster agent is registered under that id, and
the plane reconciles cleanly while never connecting. Set `planeID` to whatever the cluster-agent
charts were configured with (`default` on the showroom) and check
`status.agentConnection.connected`.

## Two org units, and why neither is `default`

This repo was laid out in namespace `default` and moved, for a reason worth knowing before anyone
relocates it back. `Environment.spec.dataPlaneRef` is **immutable once set** — upstream, at
`api/v1alpha1/environment_types.go:14` — and every quick-start install already carries
`development` / `staging` / `production` Environments in `default`. A server-side dry-run against
a 1.3.1 cluster reproduced the consequence exactly: the four regional environments validated, and
`development` was rejected with `spec: Invalid value: dataPlaneRef is immutable once set`. Flux
would then fail on that one object indefinitely, and repairing it in place means deleting an
Environment, which cascades to everything bound to it.

Its own org unit is also how the showroom models them (`growth`, `platform`), and it is where the
scenario's users and teams belong.

`quality-engineering` is the second, holding the traffic simulator. It carries **its own five
`Environment` objects and its own `DeploymentPipeline`**, with the same names and the same
cluster planes as `boutique`'s. That is not duplication for its own sake: there is no
cross-namespace reference available. `ProjectReleaseBinding.spec.environment` is a bare name with
no namespace field (`api/v1alpha1/projectreleasebinding_types.go:25-29`) and `Environment` is
namespace-scoped (`environment_types.go:34`), so a binding can only resolve an `Environment` in
its own namespace. `deploymentPipelineRef` works the same way, and there is no
`ClusterDeploymentPipeline`. Separate objects, mirrored names. Note that `spec.environment` is
immutable once set, so those five names are a one-shot decision.

## Applying it

**With Flux** — edit `flux/gitrepository.yaml` to point at wherever this ends up, then:

```bash
kubectl apply -f flux/
```

Ordering is handled, and it matters: `boutique-namespaces` -> `boutique-platform-config` ->
`boutique-projects` and `quality-engineering-projects`. The two projects Kustomizations are
separate because each org unit's tree is applied into its own namespace, so one `path` and one
`targetNamespace` cannot cover both.

> **Decided 2026-10-22: Flux owns this layer on the showroom.** The cluster had no Flux runtime —
> its content was delivered imperatively by `read-only-setup/scripts/50-projects.sh`, which walks a
> roster and `kubectl apply`s it. The split now agreed is: the **installer** keeps the org unit and
> the derived planes (it must — they carry the per-install cluster-agent CA), and **Flux owns the
> app-definition layer plus `platform-config/`**. So the `dependsOn` chain below is enforced, not
> documentation.
>
> **The installer must therefore stop applying boutique projects entirely.** Two writers over the
> same objects, with `prune: true` on the Flux side, is the first-order risk of this split — ahead
> of the release-pin collision, which only bites if someone commits a pin.

The ordering is load-bearing: a `ProjectReleaseBinding` naming an `Environment` that does not
exist yet does not resolve, so the environments have to land first.

**Without Flux** — this is also the path the showroom uses today:

```bash
kubectl apply -k namespaces/                          # both org-unit namespaces
kubectl apply -k platform-config/                     # environments + pipelines, both sets
kubectl apply -R -f namespaces/boutique/
kubectl apply -R -f namespaces/quality-engineering/
```

`-k` rather than `-R -f` for `platform-config/`, because that directory carries a
`kustomization.yaml` that `kubectl apply -f` would try to apply as an object and reject.

## Before it will work

1. **`FRONTEND_ADDR` on the load generator needs one value per environment, read off the
   cluster.** The simulator drives the storefront from its own org unit, through the data-plane
   gateway. That is the only route open to it: `namespace` visibility reaches other projects in
   the *same* namespace and no further, and a dependency entry cannot name another namespace
   (`WorkloadConnection` carries `Project`, `Component`, `Name`, `Visibility` and `EnvBindings`,
   with no namespace field — `api/v1alpha1/workload_types.go:162-187`). So it is a plain variable
   by necessity, not by preference.

   The value is the front end's gateway host for that environment, published on its
   `ReleaseBinding` status under `externalURLs` once the cell exists. The showroom's own traffic
   driver reads it exactly this way (`read-only-setup/demo/estate-traffic.yaml:110-123`). The
   workload file carries the command to read one.

   **"External" here does not mean reachable from the internet.** App endpoints are published on
   `*.openchoreoapis.localhost`, which is not publicly resolvable; CoreDNS rewrites that suffix
   to the data-plane gateway inside the cluster. External visibility means *through the gateway*,
   and app endpoints are deliberately kept off the internet. The only public surface is the
   portal.

2. **Component type names use the `deployment/*` scheme, and that is correct for the showroom —
   but it is NOT universal across 1.3.1 installs.** Verified both ways:

   - The read-only showroom's own thirteen components reference exactly this scheme —
     `deployment/service` x7, `deployment/web-application` x4, `deployment/worker`,
     `cronjob/scheduled-task` (`read-only-setup/demo/projects/*/components/*.yaml`) — and that
     estate is live on 1.3.1, so these names resolve there.
   - A stock 1.3.1 k3d install ships the **bare** names instead: `service`, `web-application`,
     `worker`, `scheduled-task`, and nothing called `deployment/*`.

   So the type vocabulary is a property of the install, not of the version. Check the target
   with `kubectl get clustercomponenttypes` and adjust if it differs — and note the corollary
   for validation: **a reference cluster is not a valid venue for checking that type references
   resolve**, only the target is. A server-side dry-run elsewhere validates CRD schemas, which
   is a different question: a `componentType` naming a type that does not exist is admitted and
   fails later at reconcile.

3. **Redis binds in all five environments here**, where the upstream sample binds development
   only. Drop the `bindings/<env>/` directories you do not want. The `Resource` is named `redis`
   but its type is `ClusterResourceType/valkey` — it has always been Valkey, and the name is
   inherited verbatim from upstream's own sample. The wiring is deliberate: the shipped `valkey`
   type sets `requirepass` with an ESO-generated password and publishes a StackExchange.Redis
   `connectionString`, which `cart` binds to `REDIS_ADDR` — correct for a .NET cartservice. Do
   not swap in a passwordless Valkey type.

4. **Every component is built from source.** All eleven carry a `workflow:` block against
   [`Ketharan/microservices-demo`](https://github.com/Ketharan/microservices-demo), built by
   `ClusterWorkflow/dockerfile-builder` on the company-wide workflow plane. `ClusterWorkflow`
   rather than a namespaced `Workflow` is what keeps every reference in this repository
   cluster-scoped and the sample clone-able.

   **Ten take `/src/<service>` as their docker context; `cartservice` does not.** It is .NET and
   nests a level deeper: `cartservice.sln` at the service root with `src/` and `tests/` beneath
   it, so its context is `/src/cartservice/src`. All eleven Dockerfile paths were verified to
   resolve on the fork before being written here. The failure mode that avoids is one build out
   of eleven failing to find a Dockerfile, deep into a run, looking like an infrastructure
   problem rather than a path problem.

   `src/shoppingassistantservice/` also carries a Dockerfile, so the assistant in `pending/` is
   buildable from this same fork rather than needing one written.

5. **`loadgenerator` stays `deployment/worker` — decided 2026-10-22.** Upstream runs Locust
   continuously, so `worker` is the faithful choice, and three things settled it: it mimics real
   user patterns; it matches the estate's existing traffic driver, which is a `while true` loop
   and not a cron (`read-only-setup/demo/estate-traffic.yaml:156`); and Hubble cell-diagram edges
   need ongoing flows, so a five-minute burst would render them intermittently — the cell diagram
   being a headline surface of this scenario.

   **The diagram is what changes.** The Google Doc's Traffic Simulator row reads
   "Shopper Bots · Scheduled Task · every 5 min", and that line is now wrong. Nothing in this
   repository needs editing for it.

## Cloning it

```bash
git clone https://github.com/Ketharan/boutique-gitops
```

That home is **interim**. The natural permanent home is the `openchoreo` org alongside
`openchoreo/sample-gitops` and `openchoreo/sample-workloads`, both public, which is what the
clone-able-public-sample goal actually asks for. The org appears in this repository only in the
clone command above and nowhere in any manifest, so moving it is a URL change here plus the one
`flux/gitrepository.yaml` line.

## Not in this repository

The AI gateway itself, and the egress policy. The gateway is platform infrastructure in
`openchoreo-data-plane`, installed by Helm, outside all five projects and owned by none of them,
so it will never live here — its `ai-llm-routing` / `ai-mcp-federation` traits attach to the
**consuming** component instead.

The two AI-dependent components *are* here, scaffolded under `pending/` with their blockers and
activation steps written down: `shoppingassistant` and the `insights` project.
