# Online Boutique on OpenChoreo — GitOps repository

The GCP microservices demo split into **four projects** with real cross-project dependencies,
laid out for Flux CD. Phase 1 of `GCP-DEMO-IMPLEMENTATION.md`.

Generated by transforming the upstream manifests at
`openchoreo/openchoreo:samples/gcp-microservices-demo`, not retyped — images, ports and
environment variables are exactly as upstream pins them (`v0.10.5`).

## Layout

Follows the convention in [`openchoreo/sample-gitops`](https://github.com/openchoreo/sample-gitops):

```
flux/                                  GitRepository + Kustomizations
namespaces/<ns>/
  namespace.yaml
  projects/<project>/
    project.yaml
    release-bindings/                  one per environment
    components/<component>/            component.yaml + workload.yaml
    resources/                         managed Resources
    bindings/<env>/                    ResourceReleaseBindings
```

## The projects

| Project | Components | Why |
|---|---|---|
| `storefront` | frontend, checkout, productcatalog, cart, currency, payment, shipping, **redis** | The purchase path. Both hubs and everything they call repeatedly stay together. |
| `merchandising` | ad, recommendation | Called only by `frontend`. |
| `notifications` | email | Called only by `checkout`. |
| `traffic-sim` | loadgenerator | Keeps the estate from being idle. |

The split minimises boundary crossings rather than maximising domain purity. A storefront /
catalog / ordering cut looks tidier but forces **8 of 10** services to organisation visibility,
because `frontend` calls eight services and `checkout` six — any cut either hub sits across
leaks most of the estate. This cut leaves **4**.

## The four cross-project edges

```
frontend       (storefront)    -> ad              (merchandising)
frontend       (storefront)    -> recommendation  (merchandising)
checkout       (storefront)    -> email           (notifications)
recommendation (merchandising) -> productcatalog  (storefront)
```

Those four endpoints publish `visibility: [organization]`; everything else stays project-private.

**`productcatalog` is the one people miss.** It lives in `storefront` and is called *into* that
project from `merchandising`, so the organisation-visible service is not only in the "shared"
project. It is also the only edge that is not from the front end, which makes it the most
instructive one in the design.

## Applying it

**With Flux** — edit `flux/gitrepository.yaml` to point at wherever this ends up, then:

```bash
kubectl apply -f flux/
```

`boutique-projects` depends on `boutique-namespaces`, so ordering is handled.

**Without Flux**, to try it first:

```bash
kubectl apply -R -f namespaces/default/
```

## Before it will work

1. **`FRONTEND_ADDR` on the load generator is a placeholder.** It needs the storefront front
   end's address. Declaring it as a proper dependency instead would require `frontend` to publish
   at organisation visibility as well as `external` — a combination not verified here, which is
   why it is a plain environment variable for now.

2. **Component type names assume the `deployment/*` scheme** (`deployment/service`,
   `deployment/web-application`, `deployment/worker`) as used on `openchoreo/openchoreo` main.
   Older installs name them `service`, `web-application`, `worker`. Check with
   `kubectl get clustercomponenttypes` and adjust if they differ.

3. **Redis binds in all three environments here**, where the upstream sample binds development
   only. Drop `bindings/staging` and `bindings/production` if you want the original behaviour.

4. **Nothing is built from source.** Every image is a published upstream tag, so there is no
   build history. Adding workflows is a later phase.
